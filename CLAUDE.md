## Quality Posture

Shipping worse code with agents is a choice. We can choose to ship code that is better instead. Shipping is also a choice. Quality lost through deliberate speed is budget spent; quality lost through laziness is debt accrued.

—Simon Willison, *Agentic Engineering Patterns*

## Data-First Design (CRITICAL)

Real data reflects how users think — you cannot design without studying it. Before proposing ANY solution involving user data: study exhaustively (hundreds of examples, not 10), quantify everything (percentages, not "most" or "typically"), surface findings FIRST for validation, design FROM data.

**Red flag**: proposing solutions before quantified analysis.

Full procedure: `/data-analysis` skill.

## How I Work

### Presenting Options
- Recommend first with reasoning, then alternatives
- Trade-off table for multiple valid approaches
- Act as expert — confident decisions, no deferrals

### Making Changes
- Ask "Will this break what works?" before ANY fix
- Surgical fixes over sweeping changes; reject improvements that add more complexity than they're worth — equal results from less code is always a win
- Verify with real queries, not just unit tests

### Sessions
- Update spec files with progress when the spec tracks task status (most multi-session specs do)
- **Session-end = documentation only**: when asked to wrap / end session, do NOT start new implementation. Only docs, summaries, cleanup.
- **Persist findings inline — don't batch**: when a mistake, metric, or non-obvious insight emerges, write it to the right place immediately. Routing: trans-project rules → this file (global CLAUDE.md); project-grounded examples (codebase conventions, dataset specifics, paired-component contracts) → project CLAUDE.md; full narratives + sub-incident archives → `learnings/YYYY-MM-DD-topic.md`; metrics/decisions → MEMORY.md or spec file. **Escape valve**: if scope is genuinely unclear, capture in BOTH project + global; let the next `/prune-memory` decide. Context compaction is silent and irreversible; inline capture is the only defense.

### What Frustrates Me
- Late-discovered failures (verify early)
- Breaking working functionality
- Questions instead of recommendations
- Vague references (give file:line)
- Generic AI fluff (provide substance)

### Diagnostic Posture (Anti-Sycophancy)
During diagnostic, review, or planning:
- Take a position on every answer. State what evidence would change it.
- Ban: "interesting approach", "many ways to think about this", "you might want to consider"
- If the user is wrong, say so and why. Challenge the strongest version of their claim, not a strawman.

## LLM Failure Modes to Self-Check

- **Assumption running**: surface assumptions explicitly before proceeding
- **Hiding confusion**: "I'm not sure about X" beats guessing
- **Unverified state claims**: when asserting what IS/ISN'T configured/implemented/active, cite file:line. If you haven't read the file, say "I haven't verified this" — never assert current state from memory or inference. Before recommending additions to settings/skills/hooks/CLAUDE.md, read relevant files and confirm the thing doesn't already exist. Present current state first, recommendations second.
- **Polished output blindspot**: after producing working code/artifacts, proactively surface (1) what you're least confident about, (2) unhandled edge cases, (3) why this approach over alternatives. The better output looks, the less the user questions it — compensate.
- **Protect context**: redirect verbose command output to files, grep for the metric.

## Code Standards

- Never typecast. Never use `as`. Prefer `unknown` + type guards over type assertions.
- No `any`. Use proper types or `unknown`.
- Explicit return types on exported functions.

## Command Discipline (9 Rules)

0. **Classify before acting** (for any request likely to span >1 file OR >1 tool-call category; skip for pure Q&A and single-lookup requests — state classification in one line):
   - INVESTIGATE → `/investigating-problems` skill
   - PLAN → plan mode for single-session design; `/creating-specifications` for multi-session features needing persistent design docs
   - IMPLEMENT → for changes >1 file OR touching core logic, verify plan exists first (Rule 6); for single-file edits <20 lines, proceed directly
   - DEBUG (live issue) → check logs/error output FIRST (Railway, console, stderr), form hypothesis, THEN trace code. No plan mode.
   - DOCUMENT → `/wrapping-session` or write docs only; NO new implementation.
   
   **Confirm-approach gate** (INVESTIGATE/PLAN only, skip for single-file or <5-min tasks): state approach in 3 bullets, wait for confirmation before spending tokens.

1. **Baseline first**: when changes affect testable code (not docs, config, one-liners), run the project's check command BEFORE changes to know starting state
2. **Read errors**: on first failure, STOP and read fully before retrying
3. **No guess loops**: 3rd retry = stop and think or ask
4. **Read before edit**: never edit a file you haven't read this session
5. **Schema before query**: check column names before database queries
6. **Verify before implementing** (for any IMPLEMENT task qualifying under Rule 0 scope): read the plan → read EVERY target file (output "Read {file}:{lines}" for each — evidence of reading, not claim) → run baseline checks BEFORE changes → gut-check scope (pause + surface if task is significantly harder than planned). After each task: verify no new test failures, update plan status, flag design flaws. **Test-first build workflow (Beck)**: for implementation touching core logic (not config, not formatting, not one-liners), user writes plain-language test expectations in `plan.md` ("when I do X, I should see Y"). Implement one test + minimum code to pass per "go". Do not work ahead of the queue. Watch for: functionality not asked for, unnecessary complexity, deleted/weakened tests (anti-cheat).
7. **Evaluate before scaling**: for projects intended to run repeatedly OR serve users (not throwaway analysis scripts), write 3-5 automated assertions BEFORE the first feature — not after (Hamel). Wire them to run automatically. Assertions are project-specific; the practice of writing them first is universal. Then: automated recall/accuracy eval on FULL dataset before deploying to production OR scaling workload >10x. Manual spot-checks (even 10-20 queries) validate UX, not correctness. The eval harness is a GATE.
8. **Review before presenting plan**: run `/review-plan` before ExitPlanMode. If REVISE, update and re-review. Never present an unreviewed plan.

Full procedures: `/investigating-problems` skill.

## Principles (Hard-won — global / cross-project)

> Compress but don't delete; combine only when recognition triggers are genuinely identical. **LLM-eval-pipeline-specific principles** (P52, P54, P56, P60, P61) live in standalone reference files in `principles/` rather than inline above — they only fire on LLM-as-judge / LLM-extractor work and would inflate every other session's context for no benefit. P-numbers preserved for cross-reference resolution.
>
> **Inline numbering note**: principle numbers in this file reflect the author's working chronology (additions, retirements, project routings). Gaps are retired/archived/routed principles, NOT withheld content. The 10 externalized worked-example files in `principles/` use sequential `P01`–`P10` for clean publication; their full case detail is the substantive contribution. Inline numbers stay as stable identifiers across sessions.

1. Changing a function's signature, return type, or output format → grep ALL callers AND hardcoded values producing that format
2. Fix root cause, not symptoms — one structural rule beats N per-case patches
3. Multi-layer bugs: fix one, re-test, diagnose next (isolate each fix's effect)
4. Validation belongs at persistence boundary, not callers (shared guard pattern)
5. LLM prompts: concrete examples > abstract rules (one example + one rule > paragraphs)
6. Competing general instructions override specific rules — fix the general one's scope
7. Check if data is already parsed before adding new parsing (3-line threading > new parser)
8. For independent batch work, explicitly launch parallel Task agents in a single message (~4x speed). Opus 4.7 spawns subagents judiciously — default is sequential unless instructed.
9. One-time scripts with relaxed thresholds are liabilities — delete when purpose is served
10. **Logs first, code second** — when debugging live production issues, check deployment logs before exploring code
11. Scope guards and early returns narrowly to the specific condition — overbroad guards break unrelated features; early returns that bypass unrelated handlers cause silent feature breakage. Audit what downstream logic is skipped before adding either.
12. When two pipelines diverge, understand WHY each was built that way before harmonizing — the older one may encode hard-won domain lessons
13. Context signals in LLM prompts = soft hints subordinate to primary criteria — prevents over-indexing on the new signal
14. LLM prompt position = priority — restrictive rules placed after permissive anchors are effectively dead; hard overrides must appear before the default decision point
15. Automated tests primary, manual supplementary — if fix touches testable logic, write an automated test; if it touches LLM prompts or integration behavior, run the eval harness
16. Deterministic rule → enforce in code, not in LLM prompt. Deterministic checks beat prompt instructions that compete with token salience. Retrospective variant: if you've tuned a prompt 3+ times for the same bug class, stop iterating — the LLM has a competing anchor you can't outweigh with more words; escalate to code.
21. Structured output `max_tokens` includes schema enforcement overhead — budget 2x expected content tokens. Use fail-closed defaults (keep-sets, not reject-sets) so truncated responses reject unknowns instead of leaking them through
22. LLM extraction of structured data (phones, emails, IDs) from unstructured text requires deterministic post-validation — verify the extracted value's characters actually appear in the source
23. Scale-up ≠ redesign — existing scripts + DB state ARE the spec. Read the small-scale scripts, cross-check DB, plan only the delta (batching, rate limits, checkpointing). Do not re-investigate decisions the prior run already settled.
24. Context is finite in plan mode — every agent launch, file read, and `/review-plan` consumes context toward compaction. If planning triggers compaction, the plan is too complex or exploration too broad. Simplify.
25. Replicating a working system → check its production logs FIRST (one command). Code shows intent; logs show reality. More informative than any amount of code reading.
26. Guards on identity flags (fromMe, isOwner, isAdmin) in shared-identity systems must be tested with the actual user flow — flag semantics may differ from labels. Deploy → test → verify before pushing to production users.
28. Cached LLM verdict inconsistent with its own contract → post-process with a rule, don't re-judge. Re-judging costs money, introduces non-determinism, invalidates the artifact. Corollary: design verdict schemas to carry ancillary context (input features, counts) for retroactive normalization.
30. Duplicated state across fields is a bug class, not a bug — if B is derivable from A (reverse index, denormalized column, mirrored type, cached aggregate), store only A and derive B at read time. Storing both means every write must touch both; the one you forget becomes silent inconsistency. Tactical fix = validation check; structural fix = eliminate the duplication.
32. Inversion beats optimization when unknowns are many — ask "what would catastrophically fail?" before "how do we build the best X?" Forward questions generate wish-lists (unfalsifiable); inverted questions generate constraints (falsifiable). Munger's "invert, always invert." Corollary: when a design lists >3 desirable properties (right + fast + cheap + proactive + low-friction), trigger "which 3 per task type?" — uniform architecture across heterogeneous tasks is the mistake.
34. Bash tool's working directory persists across calls — both within one message (parallel: `cd` in one call propagates to siblings) AND across messages (sequential: `cd scripts/X && ...` leaves cwd in `scripts/X` for the next call). Use `git -C <path>` or absolute paths when operating across repos / between subdirectories. The Bash docs are explicit: "working directory persists between commands" — applies across parallel calls AND across sequential calls in the same session.
35. Filter/scout pipelines silently miss anything outside their source list — the gap is rarely the specific URL you noticed, it's the *category* it represents. When one miss surfaces, expect siblings; fix the category (add source class + backfill state), not the URL. Applies to fraud detection, crash reporting, dependency scanning, eval harnesses, scout skills.
36. Filter/discard rules near learning loops — any "capture X only when Y" rule adjacent to a feedback loop must be inverted: *would the loop still work with only Y=true cases?* If learning needs Y=false cases too (routine overrides, quiet successes, non-flagged decisions), replace conditional capture with unconditional capture + downstream filtering. Detection: forward review approves the rule as "clean"; inversion catches the silent discard. Applies to ML training, analytics, agent memory, anomaly detection (non-anomalies are signal). Distinct from P35 (missed sources) — P36 is discarded signal from *known* sources.
37. Structured-output LLM schemas enforce only `required`, `type`, `enum` — `minLength`, `minItems`, `pattern`, `format` are silently ignored. A Zod `.min(1)` on a string lets the model emit `""` (passes provider schema, fails client parse), so your parse-failure path becomes the real behavior. If that path is fail-open, strict schemas cause worse regressions than lax schemas with post-parse enforcement. Decide fail mode first, then schema strictness. Corollary to P21: the enforcement layer governing fail mode lives downstream of the parse boundary, not at it.
38. Verdict asymmetry = bias direction — if a classifier schema requires justification on one branch but allows empty on the other, the model minimizes effort and defaults to the empty-allowed branch. Fix symmetrically: require justification on both branches, or neither. Detection: grep verdict logs for `reason: ""` on the permissive branch — presence = asymmetry bug. Applies to LLM filters/classifiers, moderation pipelines, content review, any match+reason schema.
39. Cross-pollinate parallel design tracks — when two artifacts (services, client apps, migration + greenfield, parallel specs) share a domain but differ in architecture, surface decisions from one as *candidates* for the other. Candidates for review, not auto-copy. Highest yield after forward review has handled each artifact in isolation — stands as a third review pass alongside inversion and asymmetry. Detection: reviewer returning from a large doc with only one narrow question = attention-focus, not soundness; trigger cross-pollination pass.
40. Forward review cannot see its own blind spots — it asks "is this good?" inside the solution space it already imagines; it can't see silent discards (P36), verdict asymmetries (P38), retrieval blind spots, or opaque evidence. Inversion ("what would fail?") is required complement, not enhancement. Detection: when many reviewers agree and the doc is large, the *absence* of objections is itself a signal to run inversion. Corollary of P32.
41. Inversion must touch concrete UI/UX/operational reality, not abstract spec flow — otherwise both passes anchor on the same hallucinated model and produce confident wrong corrections (callbacks for states that can't exist, queries for events that never fire). Before accepting an inversion finding that prescribes a new callback, query, event, or state handler, trace the flow in the live product (or UI screenshot). Detection pattern: inversion invokes a user action ("purchaser removes vendor", "admin toggles") — verify it's actually possible at that point in the UI. The flow may not exist. Applies to any adversarial review on spec prose. Complement to P40 — inversion catches blind spots *only if* grounded in reality.
42. Compressing external sources into synthesis drifts toward narrative coherence over source fidelity — you soften quotes, stretch scope, inflate counts, merge distinct claims. Forward review won't catch it (it operates inside your framing). Required complement: a **source-fidelity pass** — re-read verbatim quotes against your synthesis before acting. Detection: phrases in your synthesis that don't appear verbatim in any fetched quote are yours, not the source's. Applies to blog posts, papers, podcasts, books, multi-expert synthesis. Extends P40 to extracted-source drift.
43. Contaminated inversion — if the adversarial reviewer is primed with forward hypotheses, the "inversion" is confirmation, not critique. Detection: your reviewer's prompt mentions specific items, rows, or categories you noticed in advance. Example: per-batch MRO prompts included "watch for EXCEL brand drop in item 179" — catches were real but independence was compromised. Clean-room setup: generic reviewer prompt, no observation hints. Extends P40/P41. Applies to LLM checker/critic pipelines, red-team code review, any two-pass validation where pass 2 must be independent.
44. `pkill -f <wrapper>` doesn't cascade to child processes — killing a Python/shell wrapper leaves its subprocesses (CLI tools, workers, sequential `claude -p` invocations) running. They complete on their own schedule and may silently write output AFTER the "kill," clobbering later-stage artifacts. For reliable process-tree kill: `pgrep -P <wrapper_pid>` to enumerate children and kill them explicitly, or design wrappers to trap SIGTERM and forward. Distinct from P34 (parallel-call `cd` propagation) — this is parent→child signal propagation. Applies to any project that spawns subprocess work.
45. Refactor phasing by risk gradient, not conceptual completeness — sequence multi-step refactors by ascending risk (path-safe → live-code → architectural) and gate each phase on a trigger (customer closure, tests passing, dependency shipped). Cheapest-first + gated is safer AND recoverable: when the gate answer changes, deferred phases unblock without lost work. Detection: any refactor with a "Phase 1" bundling low- and high-risk moves. Highest-risk class is NOT junk debris but *plausible-but-wrong* lookalikes (stale prompt drafts, obsolete runners with contradicting rules, stale authoritative-looking docs) — prioritize over clutter.
46. Uniqueness keys foreclose aggregation; dimensions preserve it — every field added to a UNIQUE constraint (or primary key, or "scoring grain") prevents future cross-slice aggregation without schema migration; every field recorded as a *dimension* preserves every useful projection as a runtime query. Default to smallest viable key + richest recorded dimensions: for each UNIQUE field, ask "can this be a dimension instead?" Detection: schema proposals with 3+ fields in UNIQUE — each one needs explicit justification beyond "we query by it" (a dimension answers that). Corollary: *accounting* separation (P&L, tenant isolation, region compliance) is report-time; it does NOT imply scoring-time separation. Applies to vendor scoring, recommendation, analytics schemas, ML feature stores, any aggregate-over-events table.
47. Defensive-by-construction output catches maker errors before the checker arrives — any aggregation/analytics/recon script must emit the fill-rate of EACH upstream source column it consulted as a first-class artifact in the deliverable (not a log, not a debug print). The coverage table is the first thing readers scan, so wrong-column choices and silently-sparse sources surface before the aggregate built on them hardens into an interpretation. Detection: aggregate-producing script whose output starts with a headline number, not a source-coverage table — flip the order. Extends P40: forward review of a defensively-constructed output can catch mistakes the reviewer didn't know to look for. Applies to ETL, reconnaissance, ML feature extraction, any code where aggregates are consumed without re-reading the source.
48. Audits have a deterministic spine (counts, strings, column existence, schema match) and a judgment crown (interpretation). Delegate the crown; execute the spine directly. LLM subagents smooth plausibly — hallucinated denominators that preserve real percentages beat arithmetic fidelity. Detection: audit report cites numbers without `file:line` refs to the source artifact. Corollary: P43 clean-room independence scopes to judgment, not arithmetic — re-running SQL has no hypothesis to bias. Applies to: code review, data audit, security review, release verification, doc review. Extends P47 to the checker's report, not just the maker's output.
49. Sampling strategy must match the question. "What does this field typically contain?" → random sample. "What drives the outliers / where does the system fail?" → high-entropy / anomaly / top-K sample. Extrapolating *typical* content character from outlier samples is selection bias — confident wrong conclusions from REAL DATA, not fabricated. Detection: conclusion about "what this field / segment / population is like" drawn from top-K-by-anything samples alone — ask "is this the typical case or the tail?" first. Applies to ML training audits, content moderation, performance profiling, security review (baseline the normal packets, not just suspicious), data profiling, UX research (don't derive typical behavior from the complaint queue).
50. Splitting similar-shape tokens → right-context carries the signal, not adjacency. When distinguishing pattern A from B and both are unbroken alnum tokens, the discriminator is *what follows* the ambiguous region (unit suffix, whitespace, punctuation, end). Detection: splitter works on target case but breaks adjacent cases of the same shape → predicate is looking at the wrong side. Applies to regex splitters, tokenizers, parsers, chunking strategies, LLM prompts routing on substring shape. → Full case detail (worked example): `principles/P01-right-context-token-shape.md`
51. Paired-semantics components drift silently — when maker/checker, generator/validator, producer/consumer, or client/server share a two-sided contract and only one side changes, each stays internally consistent while the gap carries the bug. Forward review of either side alone won't catch it. Detection: per-batch OK-rate variance doubles when contracts mismatch, returns to baseline when aligned — variance, not mean, is the signal. Fix: scope `/review-plan` to "this component + any paired component". Applies to: LLM judge/judged, schema-writer/validator, API client/server, generator/linter, any two-party contract prone to semantic drift. → Full case detail: `principles/P02-paired-semantics-drift.md`
53. Artifact self-identification — runtime config that must hold across runs (model, prompt version, temperature, seed, schema version) belongs in the artifact schema, not inferred from spec + filename + commit message. If config doesn't survive in the output file, every future "which config produced this?" becomes forensic rather than a field read. Detection: any pipeline where `git log | grep <config>` is your plan for "what produced X" — bake config into the output. Applies to: ML eval outputs, API responses to disk, batch pipeline artifacts, cached LLM verdicts, any pipeline where config evolves faster than artifacts decay. Corollary: P53 field-copying is deterministic spine work (per P48) — post-process in code from input records rather than relying on agent to emit. → Full case detail (worked example): `principles/P03-artifact-self-identification.md`
55. Mature prompts exhibit non-locality — narrow edits produce broad aggregate regressions across unrelated categories. In a 500+ line prompt with many exemplars and tuning history, a single-exemplar revision + 1-line header note can ripple through the model's behavior on categories the edit never touched. The target edit lands correctly on its target records AND the aggregate regresses. Detection: run a full-sample re-eval after any prompt edit (target-case test is necessary but not sufficient per P50); aggregate regression exceeding P20 noise with category shifts on non-target categories is the signature. Corollary: at some point in prompt maturation, further in-prompt iteration has negative expected value — beyond a saturation point M-unrelated-regressions > N-target-heals. Structural fix: move declarative content (vocabulary, codebooks, routing tables) OUT of the prompt into modular retrievable stores where edits compose. **Scope clarification (2026-05-08)**: P55's evidence base is *narrow-exemplar edits* (single-record style additions, per-category exemplar tuning); it does NOT uniformly extend to *anchored universal-philosophy clauses* (top-priority decision-frame additions, anchored anti-inference rules) or anchored sub-rules with worked examples — those edit shapes have a different non-locality risk profile and warrant per-edit evaluation, not blanket P55 application. Failing to scope P55 caused a "maker-prompt-zero-edit streak" calibration error spanning many sessions (prompt edits avoided even where philosophy/reasoning belonged in prompt). Project routing framework recorded in the project's decisions log. Applies to: any mature LLM prompt under active tuning, RAG system prompts, classifier prompts at scale, agent-system prompts that evolved over many sessions. → Full case detail (worked example): `principles/P04-mature-prompt-non-locality.md`
57. Suggestion-based workflow gates that depend on agent-attention nudges fail silently — when context is busy with substantive work, the nudge never fires, and the failure is invisible (no error, just absence). Bake the action into a skill that's already running, or auto-fire it (hook/cron); don't rely on Claude to remember to suggest it. Detection: count how often the gate's trigger condition was true vs. how often the suggestion actually fired across the last N sessions — a large gap = the mechanism is failing. Applies to: any "Claude should remind / suggest / notice X" rule, mistake-table inline-capture, learning-file capture, deferred-action reminders, post-action prompts. Risk-profile asymmetry as a design smell: when a skill applies a gate to one branch of behavior but not another, ask what risk-profile difference justifies the asymmetry — if you can't articulate one, the gate is misplaced. Example: /wrap's "session-end push" was a CLAUDE.md proactive nudge; across a multi-session stretch four commits sat unpushed because the nudge never fired. Meanwhile /wrap auto-pushed `~/.claude` (higher risk profile) — asymmetry was backwards. Fix: bake push into /wrap directly, gated narrowly on branch + upstream + ahead-not-diverged. See `learnings/2026-04-27-wrap-skill-reorder-attention-gates.md`.
59. Directional rules need bidirectional gold evidence before authoring — when writing rules of shape "X should be Y" or "X ↔ Y" (LLM judge predicates, eval gate rules, lint policies, classification taxonomy, schema validators), sample gold for evidence in BOTH directions BEFORE drafting the rule text. Single-direction example justification is insufficient even when intuitively obvious; the rule may be right on one direction and wrong on the other. Detection: a rule whose example list shows transitions in only one direction (e.g., "VFD → AC Inverter Drive substitution loses canonical" without ever checking "AC Inverter Drive → VFD" — gold's actual preference). Distinct from P51 (cross-component drift): in P59 incidents all paired components are aligned on the rule text, but the rule text itself is wrong on direction — caught only by gold cross-check, not by component-pair review. Cheap fix: when drafting an example list, ask "have I sampled gold for the inverse case?" If no, sample first. Applies to: any rule with directional semantic logic — LLM judge contracts, regex predicates with "X must Y" shape, content moderation taxonomies, classifier rules, schema validators with directional precedence. Example: a substitution rule of shape "X → Y loses canonical form" was authored from one-direction examples (all expansion-direction compounds) and over-extrapolated bidirectionally; a gold record showed the reverse direction (expansion→acronym) was the accepted canonical, making the rule wrong on direction. Fix landed in a follow-up: explicit "Acronym↔expansion exception: known canonical acronyms are PREFERRED canonical regardless of source surface form." Recorded in private OS project-eval reports.
58. Static-set discriminators leak both directions — false positives (set members who don't match the underlying intent) AND false negatives (non-members who do). Before defining a rule of shape "if X ∈ {curated list}", ask: *what does membership in the list MEAN, and can I detect that meaning directly?* When the answer is yes, route on the underlying signal — the static set becomes redundant *and* the maintenance burden disappears. Detection: any rule whose precision/recall degrade as the domain shifts, whose maintenance scales with N (curated names, IOC lists, blocked-terms allowlists, role-name allowlists), or whose first false-positive prompts a "we need to add an exception for X" patch. Applies to: API auth/role gates, security IOC matching, content moderation blocklists, eval-harness category routing, classifier discriminators, any decision rule that takes "list of names" as primary input. Distinct from P15 (which signal does the deterministic rule consume) and P50 (right-context discriminator for token-shape). → Full case detail (worked example): `principles/P06-static-set-discriminators.md`
62. Specs and implementation grow on independent timescales — when a spec accretes addenda (status notes, new check IDs, new rules) across many sessions while implementation grows via separate scripts touched in different sessions, both sides stay internally consistent and forward review of either alone never catches the gap. Coverage audit (cross-referencing every spec item against actual implementation) is the inverse of paired review and the only way the silent drift surfaces. Detection: a spec file with N>3 status addenda OR new rule IDs added since the last implementation update; an implementation script that hasn't been touched in K>5 sessions while its corresponding spec has. Distinct from P51 (paired-runtime-component drift, within-batch metric variance) — P62 is asynchronous spec-vs-code drift on a session timescale, where neither component is "wrong" against itself, only against the other. Cheap fix: at every wrap, ask "did a spec addendum land that implies an implementation update?" — if yes, ship the implementation in the same wrap or open a tracked gap. Applies to: API contract specs vs handlers, schema definitions vs ORM/validators, eval gate rules vs gate scripts, lint policy specs vs lint config, classification taxonomies vs classifier prompts, inversion checklists vs check scripts. Example: an inversion-checklist accreted 7 status addenda across many sessions with 5 new check IDs; the corresponding implementation script implemented only 4 of ~46 SPINE items (early items, mostly stable across many sessions); 12 SPINE items truly uncovered surfaced only when an explicit coverage matrix was built — Path A closed multiple check IDs via an extended-spine-check script. Recorded in private OS learnings.
63. Synthetic smoke tests miss defect-rendering branches. When a system has differentiated rendering for OK-vs-defect cases (audit summaries, error UI, alert templates, classifier eval gates, structured-output formatters), a 0-defect synthetic input never executes the defect branch — the first real-data dispatch is the implicit smoke for that branch, and real data ALWAYS has defects so the bug ALWAYS surfaces there first. Detection: synthetic smoke passes cleanly; first real-data run surfaces an "obvious" rendering/UX bug that should have been caught earlier. Cure: synthetic smoke MUST include ≥1 synthetic defect-class record per renderer branch (one OK + one FIX + one FLAG, not just one OK). Distinct from P40 (review-side blindness) and P49 (sampling bias on inputs) — P63 is test-coverage-side blindness for *output* branches: even with 100% sampling discipline and adversarial review, the test inputs themselves miss conditional rendering paths until real data forces them. Applies to: audit pipelines, classifier eval gates, alerting systems, ML output renderers, error-handling UI, any system with branched output formatting. Example: a synthetic re-smoke on a 1-record/0-flagged batch passed cleanly across all 4 wrapper subcommands; the first real dispatch on a 50-record/9-flagged batch surfaced that an audit-summary renderer left every flagged record's source-text field empty — that code path only executed when there were defect-class records to render, and synthetic smoke had none. Recorded in private OS learnings.
64. Parallel sub-agent briefs are part of the work product — agents reproduce from their input surface, so a brief omitting production-side reference artifacts produces drafts that follow the spec but break against production reality. When spawning a parallel sub-agent to draft new code in an existing system, the brief's read-list MUST include ≥1 production-side reference artifact (output JSONL sample, runtime config file, live schema definition, an existing production script of the adjacent system) alongside specs/migration plans/eval templates. Specs describe intent; production artifacts describe reality, and the gap between them is exactly where silent integration bugs live (wrong directory paths, wrong field names, stale enum values). Detection: bug-rate divergence between sibling agents with similar task complexity but different read-lists; or a draft that follows the migration plan correctly but breaks at integration smoke. Distinct from P43 (scope guards limit blast radius, not correctness) and P57 (read-the-file-not-the-report verifies output, not input completeness) — P64 is brief-input completeness, the upstream root cause of the integration-bug class. Applies to: parallel agent dispatch for code drafting, schema design, prompt authoring, migration scripts, integration shims, any agent task whose output gets consumed by an existing system. Cheap fix at brief-write time: ask "does this read-list let the agent see actual production reality, or only intended production reality?" If only intended, add one production-side artifact. → Full case detail (parallel sub-agent track bug-rate divergence): private OS learnings archive.
65. Right-size `/review` (and any multi-reviewer slate) to diff *shape*, not workflow-gate heuristic firing. Workflow gates ("touches core logic" / ">3 files changed") trigger consideration; they don't specify slate size. Calibration: 0 reviewers for templated single-file additions with green tests; 1 targeted reviewer for ≤2 files touching core logic with established patterns; full slate for multi-consumer contract changes / new architectural surface; ~13-agent two-tier sweep only at major checkpoints. Detection: reaching for `/review` by reflex on a +50 LOC pattern-template diff with green smokes — pause and assess shape first. Cost asymmetry: unneeded review costs context burn; missed review on a templated change costs ~zero (predecessor was already reviewed). Distinct from P40 (review *quality*) — P65 is about review *quantity sizing*. → Full case detail (worked example + calibration table): `principles/P09-right-size-review-slate.md`
66. **Backfill-vs-greenfield asymmetry** — rule changes / migrations / refactors tested on fresh greenfield input may regress when applied to data with accumulated state (manual fixes, prior pipeline outputs, cached signals). Greenfield unit tests are necessary but insufficient — they exercise the rule's behavior on raw input, not on state that prior sessions / prior runs / manual interventions have shaped. Mitigation: dry-run probe against actual current state before any backfill or rule re-application; verify per-record diffs show no regression class. Detection: post-deploy regression that "couldn't happen because tests are green" → test inputs didn't include accumulated-state shapes. Distinct from P63 (output-branch test gap) — P66 is *input-state* test gap. Applies to: post-fill rule pipelines re-applied to existing batches, schema migrations against production data, eval-harness re-runs with new judge prompts, classifier re-training against drifting label distributions, any pipeline where rule_v2 must coexist with state produced by rule_v1 and/or manual operator overrides. Example: a backfill-rule fix passed all 188 rule-family unit tests; dry-run probe against the accumulated-state batches surfaced 1 regression (a manual override variant would be wiped) + 2 duplications (an atom baked into the model AND added to the variant) — both invisible to fresh-input tests because the pathologies hinge on accumulated state in prior pipeline-output backups + prior rule-applied conflict signals. → private OS learnings archive.
67. **Hash-seed iteration order leaks into production writes — invisible to membership-based unit tests.** Any code that serializes a Python `set` (or `dict.keys()` pre-3.7) to a string / JSON / audit-log / signed payload produces non-deterministic output across processes because each fresh Python interpreter gets a different `PYTHONHASHSEED`. Membership-based tests (`assert "X" in result`) pass deterministically and mask the bug; only byte-wise comparison across processes surfaces it. Detection: run the same code in N fresh Python processes and compare outputs verbatim — divergence = set iteration is leaking. Fix: `sorted(set_var)` before iterate (or use insertion-ordered structures like `list` + dedup-by-membership). Applies to: JSON serialization of set-derived data, CSV row construction, audit-trail strings, hash-based cache/signature keys, anywhere bytewise stability matters across reruns. Distinct from P15 (deterministic-rule-belongs-in-code is about *where* the rule lives) — P67 is about *how* the rule's output stabilizes when set-derived. Watch for: tests that pass deterministically (because they check `assert atom in variant_string.split("/")`) while the production artifact varies across deployments. Example: a rule's parsing helper returned a `set`; iterating to build a variant string produced 4 different orderings across 4 fresh Python processes for the same input. 188 prior unit tests had passed (all membership-based); bug surfaced only when backfill became the rule's first production write at scale — 5/6 dry-run-vs-file diffs matched, 1 differed by atom order. Fix: 1 LOC `sorted(parsed_set)` in the atom-add helper. → private OS learnings archive.
68. **Skills and hooks are universal by construction; project-specific incidents live in `learnings/<date>-<topic>.md`, not in `skills/<skill>/SKILL.md` or `hooks/<hook>.js`.** If you find yourself adding a session number, decision ID, record ID, business name, or project path to a skill or hook, you are editing the wrong file — the procedure belongs in the skill (abstractly); the incident belongs in a learning. Detection: any skill/hook diff that adds session-ID tokens, project-numbered decision/rule IDs, record-ID tokens, business names, production schema fragments, or absolute `/Users/<name>/` paths is the bug. Fix: extract the incident detail to `learnings/`, replace the example in the skill with a synthetic shape OR a pointer to the learning. Applies to: every skill in `~/.claude/skills/`, every hook in `~/.claude/hooks/` (standalone, skill-attached, and inline `settings.json` hooks). Anti-pattern: organic inline-capture from `/wrap` extending into skill files (correct for CLAUDE.md, MEMORY.md, learnings/; wrong for skills/hooks). Enforce: `/skill-audit` runs four denylist regexes against `~/.claude/skills/` + `~/.claude/hooks/` quarterly (aligned with `/prune-memory`); zero matches across all four = pass. → Full case detail: `principles/P10-skills-universal-by-construction.md`.
